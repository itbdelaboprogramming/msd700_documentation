# 管理コンソール: バックアップ

<RoleBadge role="developer" />

バックアップタブ(`BackupsPanel.tsx`)は、
[バックアップ、リストア、データ移行](/ja/development/backup-and-restore)で完全に文書化されている
アーカイブ機構に対する管理コンソールのフロントエンドであり、**レンタルプロファイル全体**の
アーカイブを扱う。ユニットタブには、同じアーキテクチャのユニットスコープ半分へのより狭い独自の
入口がある(
[ユニット & フリート § このユニットのレンタルスコープデータをバックアップする](/ja/development/webui/admin-console/units-and-fleet#このユニットのレンタルスコープデータをバックアップする)
を参照)。しかしこのタブは、管理者がアーカイブを第一級オブジェクトとして管理する場所である。
作成、削除、ダウンロード、アップロード、復元だ。

## 2つのスコープ、プロファイル側の1つのタブ

[バックアップとリストア § デュアルスコープバックアップアーキテクチャ](/ja/development/backup-and-restore#_2軸バックアップアーキテクチャ)
は、`scope: 'profile'` または `scope: 'unit'` でキー付けされた2つの独立したバックアップスコープを
定義している。このタブはプロファイルスコープ側を扱う。テナント中心のアーカイブであり、「レンタル
プロファイルが所有するすべてのマップ、ルート、エリア、プレイリスト」を、そのプロファイルが使用した
あらゆるロボットにわたって捕捉し、失われたロボットを再マッピング可能な形で、新しいプロファイル(管理者が選べば既存のプロファイル)へ
追加的に復元する。ユニットスコープ側、すなわち1台の物理ユニットがこれまでに記録したすべての履歴を扱う
ロボット中心のアーカイブは、代わりにユニットタブから到達する(上記参照)。

## プロファイルのアーカイブを作成する

`POST /admin/api/profiles/:id/backups`は、[バックアップとリストア § アーカイブ構造](/ja/development/backup-and-restore#アーカイブ構造-tar-gz)
に記載された構造の`.tar.gz`アーカイブを生成する。内容は`manifest.json`(プロファイル行、メンバー、
ユニット割り当て、および各マップとその配下のルート・エリア・プレイリスト)と、各マップの
`<mapId>.pgm`、`.yaml`、`.png`を収めた`files/`ディレクトリである。アーカイブにSQLダンプは含まれない。
ファイルが既に失われていたマップもルートとエリアは保持され、レスポンスに一覧が返される。

::: info アーカイブに含まれるもの、含まれないもの
含まれるもの: プロファイル自体、ユニット割り当て、所有するすべてのマップ・ルート・エリア・プレイリスト、
およびそれらが参照するマップ画像ファイル。**オペレーターアカウントは決して含まれない。** メンバーシップは
リストア時に再リンクできるようIDとユーザー名で記録されるが、再リンク先は既存のアカウントに限られる。
`created_by` / `modified_by`は帰属情報として保持され、存在しなくなったアカウントを指すものは`NULL`となり
「unknown」と表示される。アーカイブのリストアが`users`テーブルの内容を作成・変更・削除することはない。
:::

## アーカイブを削除する

`DELETE /admin/api/backups/:id`はアーカイブの行とファイルを削除する。[データベーススキーマ § バックアップと同期](/ja/development/database-schema#バックアップと同期)
のとおり、`profile_backups`の行は取得元のプロファイルから独立している(`profile_id`は`ON DELETE SET NULL`、
「アーカイブはアーカイブ対象より長く存続しなければならない」)。ただし逆は成り立たない。アーカイブの削除は
アーカイブを削除するだけで、取得元の稼働中のプロファイルには影響しない。

## ダウンロード / アップロード

- **ダウンロード**: `GET /admin/api/backups/:id/download`は保存済みの`.tar.gz`を返す。ダウンロード名は
  プロファイル名から作られ、ディスク上のファイル名はバックアップのULIDである。
- **アップロード**: `POST /admin/api/backups/upload`はアーカイブを**生のリクエストボディ**として受け取る
  (multipartではない)。サーバーは内容を検証し(誤ったファイル形式、破損したgzip、新しすぎる形式バージョンは
  拒否)、`profile_id`が`NULL`の新しいバックアップ行として保存し、リストア計画をそのまま返す。

## リストアを計画する

`POST /admin/api/backups/:id/plan`は実在するエンドポイントで、何も書き込まない。リストアで作成されるもの、
アーカイブ内のどのロボットが既に登録されていないか、データがどのプロファイルに入るかを報告する。コンソールは
未解決のユニットがなくなるまで、管理者の選択を`unit_remap`(アーカイブ内のユニット → 登録済みユニット)と
`profile_remap`(アーカイブ内のプロファイル → 既存のレンタル)として送り返す。アーカイブはアーカイブ対象より
長く存続するよう設計されているため、この手順が重要になる。内部の`unit_id`は、削除・交換されたロボットや、
このサーバーに存在したことのないロボットのものかもしれない。

## リストアを実行する

`POST /admin/api/backups/:id/restore`は同じ`unit_remap` / `profile_remap`でアーカイブを適用する。
未解決のユニットが残っている場合や、選択した宛先プロファイルが既に存在しない場合は、計画を添えて`409`を返す。

::: warning リストアは常に追加的である
既存のものが変更・上書きされることはなく、リストアは行とファイルを追加するだけである。元のULIDは空いていれば
再利用され、そうでなければ新しいULIDが発行されてすべての参照が付け替えられる。`profile_remap`がない場合、
プロファイルのアーカイブは常に**新しい**プロファイルに入る(元のULIDと名前が両方空いていれば再利用)。
同じアーカイブを2回リストアすると2つのプロファイルができる。煩雑だが破壊的ではない。「置き換え」モードはない。
:::


バックアップが触れるテーブル(`profile_backups.scope`、同期テーブルなど)のスキーマ進化は、
[バックアップとリストア § スキーマ移行スクリプト](/ja/development/backup-and-restore#スキーママイグレーションスクリプト)
にある移行スクリプトによって処理され、このタブの何かによるものではない。それらはデータベースに
対して直接実行され、`BackupsPanel.tsx` の対象外である。
